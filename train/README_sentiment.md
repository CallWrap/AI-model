# F3 상담등급 — 감정 분석 기반 판정

> ⚠️ **이 문서의 점수는 재현 데이터 기준 내부 지표다. 대외 발표·보고서 인용 금지.**
> 등급 라벨 186건은 전부 검수 전이다(생성 시점 값 + LLM 초안). 명세 9.1 참고.

민원인 발화의 감정을 점수로 매기고, 그 점수를 2축 규칙에 넣어 **칭찬콜 / 악성콜 / 일반**을
판정한다. 전 과정이 **인터넷 없이** 돈다.

---

## 1. 결과 요약

**악성콜 Recall 0.9630 (26/27건)** · Macro-F1 0.7559 · Accuracy 0.85

|  | precision | recall | f1-score | support |
|---|---|---|---|---|
| 악성콜 | 0.96 | **0.96** | 0.96 | 27 |
| 일반 | 0.88 | 0.92 | 0.90 | 131 |
| 칭찬콜 | 0.47 | 0.36 | 0.41 | 25 |

```
              예측 칭찬  예측 악성  예측 일반
실제 칭찬  25건      9       0      16    ← 일반으로 흘림 (감수)
실제 악성  27건      0      26       1    ← 1건만 놓침
실제 일반 131건     10       1     120
```

**악성콜을 놓치지 않는 것이 최우선이다** (명세 7장). 악성콜을 일반으로 표시하면 아무도
모르고 넘어가지만, 일반을 악성으로 표시하면 상담사 검토에서 걸러진다. 손해가 비대칭이다.
같은 이유로 **칭찬콜을 일반으로 흘리는 것은 감수한다.**

### 칭찬콜은 약하다

25건 중 7~9건만 잡는다. 감정 점수만으로는 한계로 보인다. 통화 끝의 "감사합니다"가
칭찬콜에도 일반콜에도 나오기 때문이다. 진짜 칭찬콜은 "상담사분 친절하시네요" 같은
**상담사를 향한 평가**인데, 그건 감정의 세기가 아니라 내용의 문제다.

## 2. 판정 규칙 — 왜 축이 두 개인가

```
score_min  < -0.70  → 악성콜     가장 격한 발화가 얼마나 격했나
score_tail >  0.75  → 칭찬콜     통화가 어떻게 끝났나
그 외                → 일반
```

임계값은 `config/grade_rule.json`에 있다. **코드에 박지 않는다** — 3-tier UI의 90/60처럼
근거 없는 값이 굳어지는 것을 막기 위해서다 (명세 4.5). 데이터가 늘면 다시 맞춘다.

### 한 축으로는 안 된다 (183건, 5겹 교차검증)

| 규칙 | Macro-F1 | 악성 Recall | 칭찬콜 F1 |
|---|---|---|---|
| **2축** | **0.7208** | **0.9259** | **0.33** |
| `score_min` 하나 | 0.6057 | 0.9630 | **0.00** |
| `score_tail` 하나 | 0.6727 | 0.8519 | — |

`score_min`만 쓰면 **칭찬콜 25건을 전부 일반으로 흘린다.** 칭찬콜도 시작할 때는 문제를
말하러 전화한 것이라 최저점이 낮다. `score_tail`만 쓰면 악성 Recall이 0.85로 떨어진다.
각 축이 잘하는 등급을 따로 맡긴다.

### 어느 구간을 볼지도 재서 골랐다 (EXAONE 기준)

| 축 | 보는 구간 | Macro-F1 | 악성 Recall |
|---|---|---|---|
| `score_tail` | 후반 1/3 | **0.6727** | 0.8519 |
| `score_mean` | 전체 | 0.6234 | 0.8889 |
| `score_min` | 가장 격한 발화 하나 | 0.6057 | **0.9630** |
| `score_head` | 초반 1/3 | 0.5373 | 0.6296 |
| `score_delta` | 후반 − 초반 | 0.4735 | 0.1852 |

**초반이 가장 약하다.** 통화를 시작할 때는 악성콜이든 일반콜이든 다 부정적이다 —
불만을 말하러 전화한 것이니 당연하다. 갈리는 건 그 다음이다. 상담사가 해결해주면
풀리고 못 풀면 격해진다. 그 결과가 후반에 남는다.

"처음에 화내고 나중에 풀리는 콜"은 **악성콜이 아니라 잘 처리된 일반콜**이며,
후반 축이 이걸 제대로 일반으로 잡는다.

`score_delta`(악화 정도)가 꼴찌인 것도 같은 이유다. **악성콜은 처음부터 끝까지 나쁘다.**
변화가 없어서 delta가 0에 가깝고, 잘 풀린 일반콜은 delta가 크다.

### 임계값을 더 풀면 손해다

| 악성 임계값 | 악성 Recall | 잡은 수 | 오탐 | Macro-F1 |
|---|---|---|---|---|
| −0.75 | 0.9630 | 26/27 | 1 | 0.7559 |
| **−0.70 (현재)** | **0.9630** | **26/27** | **1** | **0.7559** |
| −0.65 | 1.0000 | 27/27 | **21** | 0.6591 |

−0.65로 풀면 27건을 다 잡지만 오탐이 1건에서 21건으로 뛴다. 1건 더 잡자고 상담사가
20건을 헛되이 검토하게 된다.

## 3. 모델 선택 — 세 방식을 재서 골랐다

같은 183건, 같은 규칙, 5겹 교차검증으로 비교했다 (`eval/compare_sentiment.py`).

| 방식 | 파라미터 | 라이선스 | Macro-F1 | 악성 Recall |
|---|---|---|---|---|
| Gemma 3 12B | 12B | Gemma Terms (상업 가능) | **0.7191** | 0.8148 |
| **EXAONE 3.5 7.8B** | **7.8B** | **NC (비상업)** | 0.6727 | **0.8519** |
| 전용 감정모델 (KoELECTRA) | 0.11B | MIT | 0.4516 | 0.5185 |

### 전용 감정 모델이 진 이유

**무감정 클래스가 없어 중립 문장이 angry로 쏠린다.**

```
"제공기관 정보를 어디서 확인하면 되는지 알고 싶어요."   (중립 문의)
  전용 감정모델   angry 0.874    ← 틀림
  EXAONE         +0.2           ← 맞음
  Gemma           0.0           ← 맞음
```

모든 통화의 angry가 높게 깔려서 상대 비교가 무뎌진다. 역설적으로 `angry`를 재는 것보다
`happy`가 **없는 것**을 재는 편이 나았다(`happy_mean` 0.4516 vs `-angry_mean` 0.3295).

### EXAONE을 고른 이유 — 성능만으로 정하지 않았다

| | Gemma 12B | EXAONE 7.8B |
|---|---|---|
| Macro-F1 | 0.7191 | 0.6727 |
| 악성 Recall (최우선) | 0.8148 | **0.8519** |
| 통화 1건 처리 | 7.4초 | **3.9초** |
| 크기 | 8.1GB | **4.8GB** |
| 국가 | 미국 (Google) | **한국 (LG)** |

1. **최우선 지표인 악성콜 Recall이 EXAONE이 높다.** Macro-F1은 0.05 뒤지지만 183건
   기준으로 큰 차이가 아니다.
2. **속도가 두 배 가깝게 빠르다.** 시연에서 응답 속도가 체감 품질에 직결된다.
3. **국산 온디바이스 모델**이라는 점이 7/29 회의에서 확인된 기관 최대 니즈(보안·데이터
   미유출)와 맞물린다.
4. 중국 모델은 국가기관 도입이 불가하여 Qwen 계열은 후보에서 제외했다.

> ⚠️ **EXAONE은 비상업(NC) 라이선스다.** 실증 단계에서는 쓸 수 있으나 실제 도입 시에는
> 교체 검토가 필요하다. 발표에서 "이 모델로 도입 가능하다"고 말하지 않는다. Gemma는
> 상업 이용이 가능하므로 도입 시 대안이 된다. 최종 판단은 지도교수·산학협력단 확인을
> 거친다.

## 4. 처리 시간

MacBook Pro M5 · 32GB · 통화당 고객 발화 평균 6.7개 기준이다.

| 구간 | 시간 |
|---|---|
| 모델 최초 로딩 (프로세스당 1회) | 2.09초 |
| 중분류 + 소분류 분류 | **0.15초** |
| 감정 분석 (EXAONE, LLM 호출 1회) | **4.03초** |
| `analyze()` 전체 | **3.70초** |

**시간의 대부분이 LLM 호출이다.** 분류 모델 두 개는 합쳐 0.15초로 사실상 공짜다.

전체 데이터 처리 실측:

| 모델 | 186건 | 통화당 |
|---|---|---|
| EXAONE 3.5 7.8B | 719초 (12분) | 3.9초 |
| Gemma 3 12B | 1383초 (23분) | 7.4초 |

### 실서비스 규모에서는 어떤가

기관 현황은 연 34만 건이다. 하루 약 930건이고, 통화당 4초면 **하루치를 약 1시간에
처리한다.** 노트북 한 대 기준이다.

배치 처리이므로 감당된다. 실시간 처리(통화 중 분석)는 확장 영역으로 분리했다
(2026-07-29 회의).

### 사양이 낮으면 느려진다

LLM은 토큰 하나를 만들 때마다 모델 가중치 전체를 읽는다. 그래서 **메모리 대역폭이
속도를 결정한다.** 순서대로 영향이 크다.

| 요인 | 영향 |
|---|---|
| **RAM 부족** | 4.8GB 모델이 안 올라가면 디스크로 밀려나 수십 배 느려지거나 실패한다. 최소 8GB, 권장 16GB 이상 |
| **GPU·통합메모리 없음** | CPU만 쓰면 수 배 느려진다. Apple Silicon은 통합 메모리라 대역폭이 넓어 유리하다 |
| 모델 크기 | Gemma 12B가 EXAONE 7.8B보다 1.9배 느렸다. 같은 기기에서도 크기에 비례한다 |

분류 모델(0.11B)은 CPU에서도 빠르므로 영향이 적다. **느려지는 건 감정 분석 구간이다.**

기관 서버에 GPU가 있으면 노트북보다 빨라지고, 사양이 낮은 PC면 통화당 10~30초까지
늘어날 수 있다. 배치 처리라 치명적이지는 않으나 도입 시 사양 산정이 필요하다.

## 5. 재현 방법

```bash
# 1) ollama 설치 후 모델 받기 (여기까지만 인터넷 필요)
brew install ollama && brew services start ollama
ollama pull exaone3.5:7.8b

# 2) 등급 데이터셋 조립
uv run python eval/build_grade_dataset.py

# 3) 발화별 감정 점수 (통화당 1회 호출, 캐시되어 이어하기 가능)
uv run python train/sentiment_llm.py --model exaone3.5:7.8b

# 4) 등급 판정·채점
uv run --extra train python train/grade_predict.py
uv run --extra train python train/grade_predict.py --sweep     # 임계값별 성능

# 비교군
uv run --extra train python train/sentiment_score.py           # 전용 감정 모델
uv run python train/sentiment_llm.py --model gemma3:12b
uv run --extra train python eval/compare_sentiment.py          # 세 방식 비교
```

**모델을 한 번 받으면 인터넷이 필요 없다.** ollama는 `127.0.0.1`에만 붙고 가중치는
로컬 디스크(`~/.ollama/models`)에 있다. 상담 내용이 기기 밖으로 나가지 않는다.

## 6. 데이터

`eval/datasets/grade_dataset.jsonl` 186건 — 일반 132 / 악성콜 28 / 칭찬콜 26.
원본 골든셋 96건 + 소분류 증강분 90건이며, 소분류 작업에서 만든 데이터가 등급 쪽
최소 클래스를 16건 → 26건으로 올려줬다.

발화는 `index` · `role` · `text`로 보존한다. **감정 분석은 민원인 발화만 대상으로 한다.**
상담사 발화에는 "안 됩니다" 같은 안내가 많아 섞으면 불만으로 잡힌다. 실측으로도
상담사 점수는 세 등급에서 거의 같았다.

| 등급 | 상담사 angry 평균 |
|---|---|
| 악성콜 | 0.219 |
| 일반 | 0.225 |
| 칭찬콜 | 0.207 |

상담사 발화 점수는 나중에 **기관 평가기준표**(상담사 응대 품질 채점)에서 쓴다.

### 감정 표지 제거

생성 대본에는 `(욕설)` · `(한숨)` 같은 표지가 있고, **27건 전부가 악성콜이다.**
지우지 않으면 모델이 내용이 아니라 괄호만 본다. 실제 STT 전사에는 없는 표지이므로
`strip_emotion_markers()`로 제거한 뒤 채점한다.

| | 악성콜 angry 평균 |
|---|---|
| 표지 유지 | 0.6704 |
| 표지 제거 | 0.6605 |

**차이가 0.01뿐이다.** 표지를 지워도 어조가 문장에 남아 있다. 재현 데이터가 표지에
의존하지 않는다는 뜻이라, 실데이터에서도 비슷하게 동작할 가능성이 높다.
