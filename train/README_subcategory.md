# F2 소분류 파인튜닝 — 결과와 재현 방법

> ⚠️ **이 문서의 점수는 재현 데이터 기준 내부 지표다. 대외 발표·보고서 인용 금지.**
> 개발명세 9.1 참고. 소분류는 명세상 **보조 출력**이며 성능 목표(Macro-F1 ≥ 0.85)는
> 중분류에만 적용된다.

상담분류 **소분류 29종**을 `klue/roberta-base` 파인튜닝으로 분류한다.
중분류 문서는 [README.md](README.md) 참고.

## 1. 결과 요약

**Macro-F1 0.4636 ± 0.0661** (정답 중분류 마스킹, seed 42/7/2026 평균)

| 조건 | seed42 | seed7 | seed2026 | 평균 | 표준편차 |
|---|---|---|---|---|---|
| 마스킹 없음 | 0.3092 | 0.4023 | 0.4092 | 0.3736 | 0.0559 |
| **정답 중분류 마스킹** | 0.3874 | 0.4989 | 0.5046 | **0.4636** | 0.0661 |
| 예측 중분류 마스킹 | 0.2874 | 0.3783 | 0.3615 | 0.3424 | 0.0484 |

Accuracy 기준으로는 각각 0.4144 / 0.5225 / 0.3694다.

29종을 중분류 6종(0.4637)과 비슷한 수준으로 맞힌다. 마스킹 구조가 실제로 작동한다는 뜻이다.

### 세 조건을 다 재는 이유

| 조건 | 뜻 |
|---|---|
| 마스킹 없음 | 29개 중에서 고른다. 비교 기준선 |
| 정답 중분류 마스킹 | 중분류가 맞다고 가정. **소분류 모델 자체의 실력** |
| 예측 중분류 마스킹 | 중분류도 우리 모델이 예측. **실서비스에서 나올 성능** |

### 확인된 것 — 세 seed 모두 같은 방향

**1. 중분류로 후보를 좁히면 오른다 (+0.09).**
29지선다가 2~9지선다가 되고, 계층 위반이 구조적으로 불가능해진다.

**2. 그런데 중분류를 모델이 예측하면 오히려 떨어진다 (−0.03).**
중분류가 틀리면 소분류 정답이 후보에서 아예 빠져 맞힐 방법이 없어진다. 마스킹으로
얻는 것보다 연쇄로 잃는 것이 크다. **실서비스에서 마스킹을 그대로 걸면 안 된다.**

seed 42 기준 중분류 예측 정확도는 0.6757이었으나, 검증 37건 중 18건을 중분류 모델이
학습에서 이미 봤으므로 **부풀려진 값이다.** 실제 서비스 성능은 이보다 낮다.

### 개선 여지의 상한

```
현재 예측 마스킹      0.3424
중분류가 완벽하다면    0.4636   ← 정답 마스킹 점수가 상한
```

중분류를 아무리 개선해도 소분류는 0.4636을 넘지 못한다. 그 위는 소분류 데이터를
늘려야 오른다. **두 병목이 독립적으로 걸려 있다.**

### 편차가 크다

±0.05~0.07로 중분류(±0.025)의 두 배 이상이다. 검증 37건에 29클래스라 한 건이 크게
움직인다. seed 42만 보면 0.3874, 3회 평균은 0.4636 — **0.08 차이다.**
단일 실행으로 판단하면 안 된다는 것이 실증됐다.

## 2. 재현 방법

```bash
uv sync --extra train

uv run --with openpyxl python eval/finalize_subcategory.py     # 검수 반영 → 골든셋 93건
uv run python eval/generate_scenarios.py --sub-topup           # 부족분 90건 생성 (LLM 배치)
uv run --extra train python eval/diagnose_leakage.py \
    data/scenarios/scenarios_sub.jsonl eval/datasets/golden_subcategory.jsonl
uv run python eval/build_subcategory_dataset.py                # 합본 183건
uv run --extra train python train/split_subcategory.py         # 학습 146 / 검증 37
uv run --extra train python train/train_subcategory.py         # 학습·채점·저장

for s in 42 7 2026; do
  uv run --extra train python train/train_subcategory.py --seed $s
done
```

합본(`eval/datasets/subcategory_dataset.jsonl`)은 커밋된다. 분할·모델은 `data/` 아래라
커밋되지 않으므로 위 명령으로 재현한다.

## 3. 데이터

**183건 = 확정 골든셋 93 + 증강 생성 90**

| source | 건수 | 내용 |
|---|---|---|
| `human` | 11 | 계층 위반 15건을 사람이 검수한 결과 |
| `draft` | 82 | 검수 전 초안. 학습에는 쓰되 성능 주장 시 단서를 붙인다 |
| `generated` | 90 | `--sub-topup` 으로 생성한 증강분 |

### 증강 전에는 측정 자체가 불가능했다

| | 증강 전 | 증강 후 |
|---|---|---|
| 데이터 | 93건 | 183건 |
| 등장 소분류 | 24 / 29종 | **29 / 29종** |
| 검증셋 커버리지 | 0건인 클래스 다수 | **전 클래스 1건 이상** |
| 클래스당 표본 | 1~11건 | 5~11건 |

증강의 목적은 점수를 올리는 것이 아니라 **측정이 가능해지는 것**이었다.
`교통비 지급`·`기타`·`바우처생성`·`본인부담금환급`·`캡방식` 5종은 데이터가 0건이라
모델이 영원히 예측할 수 없는 상태였다.

### 골든셋 확정 과정

중분류는 사람 검수를 마쳤으나 소분류는 초안 상태였고, **계층 정합이 15건 깨져 있었다**
(중분류에 속하지 않는 소분류가 붙음 — 예: 중분류 `대상자관리` 에 소분류 `포상금`).
중분류만 나중에 재검수되고 소분류는 옛 값이 남은 것이 원인이다.

검수 엑셀(`eval/review_subcategory.py`)로 이 15건을 추출해 사람이 판정했다.
'수정할 소분류' 칸은 해당 중분류의 소분류만 고를 수 있게 드롭다운을 걸어,
**검수 결과가 다시 계층을 깨는 일이 구조적으로 없게** 했다.

제외한 건이 7건이다.
- **스코프 밖 4건** — 청소년산모·발달재활 등 장애인활동지원이 아닌 다른 바우처 사업.
  우리 분류 체계로 담을 수 없다 (`scn-115`·`scn-128`·`scn-019`·`scn-121`)
- **맞는 소분류 없음 3건** — 로그인 오류처럼 업무 영역이 대본에 드러나지 않는 통화

제외한 건도 중분류 골든셋에는 그대로 남는다. 소분류 학습에서만 빠진다.

### 누출 진단 통과

라벨을 먼저 정하고 대본을 생성하면 라벨마다 정해진 문구가 반복되기 쉽다. 그러면
모델이 내용이 아니라 문구를 외운다. `eval/diagnose_leakage.py` 로 검사했다.

| 대상 | TF-IDF macro-F1 | 판정 |
|---|---|---|
| 신규 생성 90건 | 0.2190 | 정상 |
| 기존 93건 | 0.2733 | 정상 |
| 합친 183건 | 0.3702 | 정상 |

0.95 이상이면 누출 의심이다. 참고로 중분류 골든셋은 0.6482다.

### 증강분이 점수를 부풀리지 않았다

| 출처 | 건수 | Accuracy (seed 42) |
|---|---|---|
| 생성 | 16 | 0.4375 |
| 생성 제외 (원본) | 21 | **0.4762** |

**생성분이 원본보다 오히려 약간 어려웠다.** 증강 데이터가 쉬워서 점수를 띄운 것이
아니라는 근거다.

## 4. 마스킹 방식

29클래스로 학습하되, 추론할 때 중분류에 속한 소분류만 후보로 남긴다.

```
중분류 = 부정사용   → 신고대상 / 신고절차 / 포상금  3개 중에서만 고른다
중분류 = 대상자관리  → 9개 중에서 고른다
```

구현은 로짓에서 해당 중분류가 아닌 소분류를 `-inf` 로 만들고 argmax를 취한다.
**계층 위반이 원천적으로 나올 수 없다** — 정민 PR #11에서 DB가 정합 검증을 하지 않기로
정해져(B안) 그 책임이 AI 파트에 있는데, 이 구조가 그 요구를 자동으로 만족시킨다.

### 소분류 개수가 난이도를 결정한다 (seed 42 기준)

| 중분류 | 소분류 종수 | 검증 건수 | Accuracy |
|---|---|---|---|
| 제공기관관리 | 2 | 4 | 0.7500 |
| 지자체사업관리 | 3 | 4 | 0.7500 |
| 부정사용 | 3 | 3 | 0.6667 |
| 결제및비용지급 | 9 | 10 | 0.4000 |
| 대상자관리 | 9 | 13 | 0.3846 |
| 제공인력관리 | 3 | 3 | 0.0000 |

후보가 2~3개인 곳은 0.67~0.75, 9개인 곳은 0.40 안팎이다. 제공인력관리 0.0000은
검증 3건이라 판단 근거가 되지 못한다. **이 표는 seed 42 단일 실행이므로 참고용이다.**

## 5. 검증셋 구성 — 두 숫자를 나란히 본다

검증 37건에 생성 증강분이 16건(43%) 섞여 있다. **의도한 것이다** — 안 섞으면 클래스마다
표본이 채워지지 않아 측정이 성립하지 않는다. 다만 그 점수는 "우리가 만든 데이터를
우리가 맞힌 것"이므로 실상담 성능이 아니다.

`train_subcategory.py` 는 채점 시 `source` 별 점수를 함께 출력한다. 성능을 인용할 때는
전체 점수와 생성 제외 점수를 함께 적는다.
