## 2026-08-18 · 상담등급은 온디바이스 LLM 감정 점수 + 2축 규칙으로 판정한다 — 성진

**배경:** 회의에서 "민원인 발화별 감정을 수치화하고 평균 내어 등급 3종을 낸다"로 정해졌다.
발화별 감정 정답이 없어(가진 것은 통화 단위 등급 라벨 186건뿐) 전용 모델 파인튜닝이
불가능했고, 공개 감정 모델을 그대로 쓰는 안과 온디바이스 LLM에 시키는 안을 비교했다.

**결정:**

- **중국 모델은 후보에서 제외한다.** 국가기관 도입이 불가하다는 기관 방침이다.
  Qwen 계열 전부가 여기서 빠졌다.
- **EXAONE 3.5 7.8B를 채택한다.** 183건 5겹 교차검증 비교 결과:

  | 방식 | 파라미터 | Macro-F1 | 악성 Recall |
  |---|---|---|---|
  | Gemma 3 12B | 12B | 0.7191 | 0.8148 |
  | **EXAONE 3.5 7.8B** | 7.8B | 0.6727 | **0.8519** |
  | 전용 감정모델 (KoELECTRA) | 0.11B | 0.4516 | 0.5185 |

  Macro-F1은 Gemma가 0.05 앞서지만 **최우선 지표인 악성 Recall이 EXAONE이 높고**,
  처리 시간이 3.9초 대 7.4초로 두 배 가깝게 빠르며, 국산 온디바이스라는 점이
  7/29 회의에서 확인된 기관 최대 니즈(보안·데이터 미유출)와 맞물린다.
- **전용 감정 모델을 쓰지 않는다.** 무감정 클래스가 없어 중립 문의도 angry 0.874로
  쏠린다. 모든 통화의 angry가 높게 깔려 상대 비교가 무뎌진다.
- **판정은 2축 규칙이다.** `score_min < -0.70` → 악성콜, `score_tail > 0.75` → 칭찬콜,
  그 외 일반. 한 축으로는 안 된다 — `score_min`만 쓰면 칭찬콜 25건을 전부 일반으로
  흘리고(칭찬콜도 시작할 때는 문제를 말하므로 최저점이 낮다), `score_tail`만 쓰면
  악성 Recall이 0.85로 떨어진다.
- **초반·변화량 축은 실측으로 탈락했다.** `score_head` 0.5373, `score_delta` 0.4735로
  가장 약했다. 통화 시작 시점에는 악성이든 일반이든 다 부정적이라 변별력이 없다.
  "처음에 화내고 나중에 풀리는 콜"은 악성콜이 아니라 잘 처리된 일반콜이며, 후반 축이
  이를 제대로 일반으로 잡는다.
- **임계값은 `config/grade_rule.json`으로 분리한다.** 코드에 박지 않는다 —
  3-tier UI의 90/60처럼 근거 없는 값이 굳어지는 것을 막는다 (명세 4.5).
- **악성콜을 놓치지 않는 것이 최우선이고, 칭찬콜을 일반으로 흘리는 것은 감수한다**
  (명세 7장). 손해가 비대칭이다 — 놓친 악성콜은 발견 기회가 없지만 오탐은 상담사
  검토에서 걸러진다. 임계값을 −0.65로 풀면 27/27을 다 잡지만 오탐이 1건에서 21건으로
  뛰므로 채택하지 않았다.
- **감정 분석은 텍스트로만 한다.** 음성 감정 분석은 확장 영역이다. ① 계약상 `analyze()`는
  `Transcript`만 받고 음성은 오지 않는다 ② 우리 재현 데이터는 TTS 아나운서 톤이라
  음성에 감정이 실려 있지 않아 검증이 불가능하다 ③ 기관 실데이터도 가명처리된 전사
  텍스트로 제공된다. 지금 만든 "발화별 점수 → 집계 → 등급" 구조는 점수 출처만 바뀌면
  되므로 음성 모델이 확보되면 같은 자리에 연결된다.
- **감정 표지(`(욕설)`·`(한숨)`)를 제거한 뒤 채점한다.** 27건 전부가 악성콜에만 붙어 있어
  그대로 두면 모델이 내용이 아니라 괄호만 본다. 실제 STT 전사에는 없는 표지다.
  다만 제거해도 악성콜 angry 평균이 0.6704 → 0.6605로 0.01만 떨어져, 어조가 문장에
  남아 있음을 확인했다.
- **프롬프트는 `eval/prompts/sentiment_v1.md`로 분리한다.** 한 글자만 바뀌어도 점수가
  달라지므로 어느 버전에서 나온 수치인지 남긴다 (명세 11장). 고칠 때는 v2로 새 파일을
  만들고 덮어쓰지 않는다.

**결과 (재현 데이터 기준 내부 지표):** 악성콜 Recall 0.9630(26/27건), Macro-F1 0.7559.
칭찬콜은 25건 중 7~9건만 잡는다 — 감정 점수만으로는 한계다. 통화 끝의 "감사합니다"가
칭찬콜에도 일반콜에도 나오기 때문이며, 진짜 칭찬콜은 상담사를 향한 평가라 내용의 문제다.

**⚠️ EXAONE 라이선스:** 비상업(NC)이다. 실증 단계에서는 쓸 수 있으나 실제 도입 시
교체 검토가 필요하다. 발표에서 "이 모델로 도입 가능하다"고 말하지 않는다. Gemma 3는
상업 이용이 가능해 도입 시 대안이 된다. 최종 판단은 지도교수·산학협력단 확인을 거친다.
명세 8.2가 EXAONE을 제외했던 근거("이식 전제 프로젝트")는 7/29 회의로 전제가
"실증 단계"로 바뀌면서 조건부로 완화됐다.

**영향:** `src/callwrap_ai/grade.py`, `config/grade_rule.json`,
`eval/prompts/sentiment_v1.md`, `train/{sentiment_llm,sentiment_score,grade_predict}.py`,
`eval/{build_grade_dataset,compare_sentiment}.py`, `eval/datasets/grade_dataset.jsonl`,
`train/README_sentiment.md`

## 2026-08-18 · analyze()를 실제 판정에 연결한다 (F2·F3만) — 성진

**배경:** 중분류·소분류·상담등급 모델이 각각 완성됐으나 `analyze()`는 여전히 Step 0의
하드코딩 더미를 반환하고 있었다.

**결정:**
- **F2(중분류·소분류)와 F3(상담등급)만 실제 판정으로 교체한다.** F1 요약·F4 후속처리·
  FAQ필요는 상용 LLM 프롬프트로 별도 담당이며 아직 붙지 않았다. 세 항목은 `failures`에
  모듈명을 넣어 미구현임을 알린다.
- **모델은 프로세스당 1회만 로딩한다** (명세 4.1). `functools.lru_cache` 기반 모듈 레벨
  지연 싱글턴이다. 실측 첫 호출 2.09초 → 이후 0.03초.
- **torch·transformers를 모듈 최상단에서 import하지 않는다.** 서버 파트는 `uv sync`만
  하므로 이 둘이 없다. 최상단 import면 `from callwrap_ai import analyze`만 해도 깨진다.
  함수 안에서 늦게 불러오고 실패 시 None을 돌려 부분 실패로 넘긴다.
- **소분류 정합은 마스킹으로 구조적으로 보장한다.** 중분류에 속한 소분류만 후보로 남기므로
  어긋난 조합이 나올 수 없다. PR #11(B안)에서 AI로 넘어온 검증 책임을 이 구조가 자동으로
  만족시킨다. 안전망으로 출력 직전에 한 번 더 검사하고, 걸리면 소분류를 비운다.
- **checkpoint 경로는 `CALLWRAP_MODEL_DIR` 환경변수로 뺀다.** 기본값은 저장소의
  `data/models/`이며 개발용이다.
- **계약 테스트는 모델이 없는 환경에서도 통과해야 한다.** 값이 아니라 계약을 검사하도록
  고쳤다 — `failures`에 알려진 모듈명만 들어가는지, **실패한 모듈이 그럴듯한 값을 남기지
  않는지**, 근거 인덱스가 실존 발화를 가리키는지를 본다.

**서버 파트에 전달할 것:** `failures`에 오른 필드는 `None`이거나 confidence가 0이므로
그것으로 거른다. 모델이 없어도 동작하며 해당 항목만 빈다. 실제 값을 받으려면
`uv sync --extra train` + checkpoint + ollama가 필요하다.

**영향:** `src/callwrap_ai/{pipeline,classify,grade,preprocess}.py`, `tests/test_contract.py`

## 2026-08-18 · 소분류는 파인튜닝 + 중분류 마스킹으로 간다 — 성진

**배경:** 소분류 29종은 골든셋 93건 기준 클래스당 3건대라 학습·평가가 성립하지 않았다.
5종은 데이터가 0건이었다. 온디바이스 LLM에 맡기는 안과 데이터를 늘려 파인튜닝하는 안을
비교했다.

**결정:**
- **파인튜닝으로 간다.** 중분류·SR유형이 모두 분류기인데 소분류만 LLM이면 구조가 갈리고,
  "데이터가 늘면 좋아진다"는 개선 경로가 분류기에만 붙는다. 분류는 분류기로, 생성(요약)은
  LLM으로 나눈다.
- **증강은 없는 클래스를 채우는 용도로만 쓴다.** 전체를 부풀리는 것이 목적이 아니다.
  93건 → 183건으로 늘려 29종 전부가 검증셋에 1건 이상 들어가게 했다.
- **생성 데이터는 TF-IDF 누출 진단을 통과한 것만 쓴다.** 라벨을 먼저 정하고 대본을
  생성하면 라벨마다 정해진 문구가 반복되기 쉽다(명세 9.1). 재혁 파트에서 1차 생성 60건이
  macro-F1 1.000이 나와 폐기한 전례를 따른다. 합본 0.3702로 정상 범위였다.
- **추론은 중분류 마스킹으로 한다.** 중분류에 속한 소분류만 후보로 남긴다. 계층 위반이
  원천적으로 나올 수 없어, PR #11(B안)에서 AI 파트로 넘어온 정합 검증 책임을 구조가
  자동으로 만족시킨다.
- **스코프 밖 데이터를 제외한다.** 청소년산모·발달재활 등 장애인활동지원이 아닌 사업이
  4건 섞여 있었다. 소분류 학습에서 뺐고, 중분류 골든셋에는 아직 남아 있다.

**측정 결과 (seed 3회 평균, 재현 데이터 기준 내부 지표):**

| 조건 | Macro-F1 |
|---|---|
| 마스킹 없음 | 0.3736 ± 0.0559 |
| 정답 중분류 마스킹 | 0.4636 ± 0.0661 |
| 예측 중분류 마스킹 | 0.3424 ± 0.0484 |

**미결 — 마스킹 운용 방식:** 예측 중분류로 마스킹하면 마스킹을 안 한 것보다 **낮다.**
중분류가 틀리면 소분류 정답이 후보에서 빠져 맞힐 방법이 없어지기 때문이다. 실서비스에서
그대로 걸면 손해다. 중분류 확신도가 낮을 때 완화하는 방식을 `analyze()` 조립 시 정한다.

또한 중분류를 아무리 개선해도 소분류는 **0.4636을 넘지 못한다**(정답 마스킹 점수가 상한).
그 위는 소분류 데이터를 늘려야 한다. 두 병목이 독립적으로 걸려 있다.

**영향:** `train/train_subcategory.py`, `train/split_subcategory.py`,
`eval/{finalize_subcategory,build_subcategory_dataset,diagnose_leakage,review_subcategory}.py`,
`eval/datasets/{golden_subcategory,subcategory_dataset}.jsonl`, `train/README_subcategory.md`

## 2026-07-29 · 실데이터 학습을 확장 영역으로 분리, 재현 데이터로 완주한다 — 3자 회의(사회보장정보원·이노하이)

**배경:** 기관 실데이터 반출이 개인정보 특성상 어렵다는 것이 확정됐다. 동시에 경진대회의
평가 축이 모델 성능이 아니라 **산업 문제 해결·서비스 효용·도입 가능성**임이 확인됐다.
심사위원도 실데이터 제약을 이미 이해하고 있어 감점 요인이 아니다.

**결정:**
- **재현 데이터(FAQ 기반 생성)로 학습과 기능 개발을 전부 완주한다.** 실데이터 재학습은
  확장 영역(로드맵)으로 분리한다. 명세 Step 6은 "확보 시" 조건부로 내린다.
- 검증은 **공개 실음성 데이터**로 한다. "재현 데이터로 학습 → 공개 실데이터로 검증"이라는
  구조 자체를 방법론으로 제시한다.
- **재현 데이터의 품질이 성과물이다.** 아나운서 톤에 머물지 않고 실제 상담의 구어체·중복·
  끊김을 반영해야 검증 단계가 성립한다. 데이터 생성 개선의 우선순위를 올린다.
- 모델 지표는 **파이프라인 동작 확인용**으로만 쓴다. Macro-F1 ≥ 0.85(명세 7장)는 유지하되
  달성 여부가 프로젝트 성패를 가르지 않는다. 지표 개선보다 서비스 연결을 앞에 둔다.
- 처리 방식은 **배치**로 확정. 실시간 상담 중 처리는 확장 영역이다.

**AI 파트 영향:**
- 도메인 갭(합성 vs 실데이터) 측정은 보고서 핵심 수치에서 내려온다. 대신 재현 데이터
  품질과 서비스 연결이 올라온다.
- 캘리브레이션은 우선순위가 유지된다 — 3-tier UI가 confidence에 의존하므로 성능이 아니라
  **서비스 체감 품질** 항목이다.
- 신규 검토 대상(담당·스코프 미정): 기관 평가기준표 자동 채점, FAQ 유사도 매칭.

**영향:** `README.md`, `train/README.md`, 명세 5장·Step 6

## 2026-07-26 · analysis_results는 JSONB 본체 + 승격 컬럼 하이브리드 (#11) — 정민

**배경:** `AnalysisResult`를 JSONB 한 덩어리로 넣을지 필드별 컬럼으로 펼칠지가 열린 질문이었다.
**결정:**
- **하이브리드**: `result` JSONB에 전체를 저장하고, `consultation_type`·`consultation_category`·`grade`만 파생 컬럼으로 승격.
- JSONB를 원본으로 둔 이유: 계약이 자주 바뀐다(v0.1→v0.2). 전부 컬럼으로 펼치면 계약 바뀔 때마다 마이그레이션이다. `Judgment`(value+confidence+evidence_indices) 중첩·소분류 29종·요약이 JSON으로 자연스럽게 왕복한다.
- 승격 컬럼 3개만 둔 이유: 대시보드가 거르고 집계하는 저카디널리티 값만. 소분류·confidence·요약은 `result` 안에 둔다.
- **소분류↔중분류 정합(`SUBCATEGORIES_BY_CATEGORY`)은 DB 제약으로 걸지 않는다 (B안).** 저장 계층이 `analyze()` 판정을 재검증하지 않는다.

**AI 파트 후속:** 정합 책임이 100% AI에 있다. `analyze()` 출력 직전에 `SUBCATEGORIES_BY_CATEGORY`로 검사하고, 어긋나면 소분류를 `None`으로 떨어뜨린다. (Step 2~3에서 구현)
**영향:** `src/callwrap_ai/pipeline.py`
