# 학습 데이터 생성 과정 정리

B안(SR유형 8종 분류) 학습에 쓴 합성 대화 데이터를 어떻게, 왜 그 순서로
만들었는지 기록한다. 코드는 `src/callwrap/prompts.py`, `generate.py`,
`baseline.py`, `scripts/build_dataset.py`에 있다.

## 0. 왜 합성 데이터인가

실데이터(가명처리 대상)는 요청 후 가명처리를 기다리는 상태라 아직 쓸 수
없었다. 그 공백을 메우기 위해 **라벨 조건부 합성 생성**으로 1차 학습셋을
만들고, 실데이터가 들어오면 교체·보강하는 순서로 잡았다.

## 1. 설계 원칙 — "라벨을 먼저 정하고 대화를 만든다"

일반적인 방식(대화를 만든 뒤 사람이 라벨을 붙이는 것)은 라벨 노이즈가
생긴다. 대신 `GenSpec`으로 **목표 SR유형을 먼저 고정**하고, 그 조건에 맞는
대화를 생성하게 했다 (`prompts.py::GenSpec`, `build_user_prompt`). 생성기가
스스로 라벨을 매기지 않으므로 노이즈가 원천적으로 줄어든다.

### 생성 격자

```
SR유형(8, '기타' 제외 7종) x 업무소분류(29) x 난이도(일반/경계/복합)
```

- **업무소분류 29종**은 `TAXONOMY`(결제및비용지급, 대상자관리, 부정사용,
  제공기관관리, 제공인력관리, 지자체사업관리 6개 중분류 산하)에서 가져왔다.
  B안 라벨(SR유형)과는 별개로, **생성 다양성을 담보하기 위한 축**으로만
  쓴다 — 실제 출력 라벨이 아니다.
- **난이도 배합**은 일반 50% / 경계 30% / 복합 20% (`DIFFICULTY_MIX`).
  경계·복합 비중이 실전 성능을 좌우한다는 판단 때문에 절반 이상을
  의도적으로 어렵게 만든다.
- **`기타`**는 업무 주제와 무관한 유형이라 소분류 축을 붙이지 않고
  전체 물량의 약 4%만 별도로 생성한다.

### 혼동쌍 5종 (경계 난이도 전용)

정의서(`docs/label_definition.md`) §4의 결정 규칙을 그대로 생성 조건에
반영했다. `CONFUSION_PAIRS`:

| 쌍 | 갈림길 |
|---|---|
| 시스템오류 ↔ 고객PC환경 | 다른 PC/브라우저에서도 재현되는가 |
| 시스템오류 ↔ 사용법문의 | 정상 경로로 했는데 실패했는가, 경로를 몰랐는가 |
| 자료확인 ↔ 자료보정 | 조회로 끝나는가, 값 변경까지 가는가 |
| 정책 및 지침문의 ↔ 사용법문의 | 답이 규정인가, 화면 조작 순서인가 |
| 기능개선 ↔ 시스템오류 | 설계대로인데 불편한가, 있는 기능이 오동작하는가 |

경계 난이도는 "초반엔 상대 유형처럼 보이다가, 중반 이후 결정적 단서 하나로
목표 유형이 확정"되도록 지시한다. 복합 난이도는 두 용건이 실제로 모두
등장하되 서로 원인 관계가 아닌 별개 사안이어야 한다는 제약을 건다.

## 2. 1차 시도 — 직접 생성, 실패

API 키(`ANTHROPIC_API_KEY`)가 설정되지 않은 상태였다. 사용자가 "API 키 없이
Claude Code 자체가 학습 데이터를 만들 수 없냐"고 물었고, 가능은 하되
**같은 대화 맥락(같은 나) 안에서 순차 생성하면 스타일이 수렴한다**는 위험을
안고 시작했다.

직접 60건(`pilot_cc_01/02.jsonl`)을 생성해 TF-IDF 베이스라인
(`baseline.py`, char n-gram + 로지스틱회귀)으로 진단했더니 **macro-F1 = 1.000**
이 나왔다. 이건 좋은 신호가 아니라 **적신호**다 — 품질 게이트 기준(90% 초과
= 표현이 정형화되어 모델이 SR유형이 아니라 문구를 외운다는 뜻)을 그대로
보여준 것이다. `baseline.py`의 `QUALITY_GATE = 0.90`이 바로 이 판단 기준이다.

## 3. 원인 진단과 대응 — "진단 → 제약" 되먹임 루프

같은 대화 세션 안에서 만든 데이터는 **자기참조적 오염**(직전에 쓴 표현을
계속 재사용)과 **동일 프라이어 수렴**(같은 모델, 같은 맥락 → 비슷한 문장
구조) 두 가지 문제를 동시에 겪는다는 결론을 냈다. 사용자 질문("다양성
문제인 것 같은데, 이전 컨텍스트를 숨길 수는 없는가")이 정확히 이 지점을
짚었다.

대응은 두 갈래로 나눴다.

1. **되먹임 루프** — `baseline.py::build_banlist()`가 클래스별 TF-IDF ×
   로지스틱회귀 계수로 "라벨을 누설하는 n-gram"을 뽑는다. 이걸
   `configs/banned_phrases.json`으로 저장하고, 다음 생성의 시스템 프롬프트에
   금지어 섹션으로 주입한다 (`prompts.py::_banlist_section`,
   `build_system_prompt`). 생성 → 진단 → 금지어 갱신 → 재생성을 반복하는
   구조다.
2. **콜드 컨텍스트 서브에이전트 생성** — 메인 대화와 컨텍스트를 공유하지
   않는 서브에이전트 4개를 병렬로 띄웠다(사용자 지시: "서브 에이전트로
   진행"). 각 서브에이전트는 독립적인 API 호출과 비슷하게 이전 생성분을
   보지 못하므로, 최소한 세션 내 자기참조 오염은 끊긴다. 여기에 서브에이전트별
   페르소나·문체를 다르게 지정해 "같은 모델·같은 프롬프트에서 오는 수렴"도
   추가로 줄였다.

### 되먹임 루프에서 나온 부작용과 수정

첫 `build_banlist()` 결과에 `단말기`, `브라우저`, `취소`, `조회`, `설치`
같은 **도메인 필수 어휘**가 통째로 금지어로 잡혔다. 서브에이전트 하나(sa1)가
자체적으로 "이 금지어 때문에 '단말기' 대신 '카드리더기'처럼 부자연스러운
우회 표현을 써야 했다"고 보고해 발견했다 — 사용자가 직접 지적한 게 아니라
생성 과정에서 드러난 문제다. `baseline.py`에 다음을 추가해 고쳤다.

- `_PROTECTED_TERMS`: 단일 단어로는 절대 금지어로 잡히면 안 되는 도메인
  필수 어휘 집합.
- `_strip_josa()`: 조사가 붙은 형태(`단말기가`, `단말기는`)를 보호어와
  매칭하기 전에 정규화.
- `build_banlist(..., unigram_coef=0.75)`: 단일 단어는 보호어 예외가
  아닌 한 더 높은 계수 기준을 넘어야만 금지어로 채택되도록 상향 (여러
  단어로 된 정형 문구, 예: "개발팀에 전달하겠습니다" 같은 것만 걸리도록).

## 4. 최종 생성 결과

| 파일 | 건수 | 비고 |
|---|---:|---|
| `data/gen_sa1.jsonl` ~ `gen_sa4.jsonl` | 28 x 4 = 112 | 콜드 컨텍스트 서브에이전트 4개, 축약 규칙 위반(`collapse_fixed`) 0건 |
| `data/pilot_cc*.jsonl` | 60 | 1차 직접 생성분. 정형화 문제로 **최종 학습셋에서 제외** |

`scripts/build_dataset.py`는 기본적으로 `data/gen_*.jsonl` 패턴만 병합하므로,
1차 직접 생성분(`pilot_cc*.jsonl`)은 자동으로 빠진다. 서브에이전트 생성분만으로
품질 게이트를 통과했기 때문에 굳이 되살리지 않았다.

```powershell
python scripts\build_dataset.py --out data\train.jsonl --val-out data\val.jsonl
```

- 스키마 검증: 화자 값, 빈 발화, 최소 발화 수(4턴) 확인
- **`sr_final` 재계산**: 생성기가 붙인 최종 라벨을 그대로 믿지 않고
  `collapse()` 규칙으로 다시 계산한다. 생성기가 우선순위 규칙을 잘못
  적용했으면 `meta.collapse_fixed = true`로 표시하고 정정된 값을 쓴다.
- 발화 내용 해시로 중복 제거
- 층화 분할로 train/val 분리

결과: **학습 98건 / 검증 14건** (총 112건, 8종 라벨 전부 존재).

## 5. 품질 게이트 재확인

```powershell
python -m callwrap.baseline --data data\train.jsonl --val-data data\val.jsonl
```

최종 데이터 기준 **macro-F1 = 0.6375** (0.55~0.90 정상 범위 내). 1차 시도의
1.000과 대조된다 — 같은 진단 도구로 "정형화되어 외웠는지"를 다시 확인한
것이며, 이 값이 실전 성능의 하한선이 아니라 **다양성 진단 지표**라는 점은
`baseline.py` 상단 주석과 동일하다.

## 6. 이후 단계 (STT 노이즈, 별도 처리)

여기까지는 텍스트가 "깨끗한" 상태다. 실제 서빙 입력(STT + 화자분리 결과)과의
간극을 메우기 위한 노이즈 주입은 별도 모듈(`stt_noise.py`)에서 학습 시점에
`SRDataset.__getitem__` 단계로 확률적으로 적용한다 (생성 단계에는 넣지 않음
— 시스템 프롬프트에도 "STT 노이즈는 후처리 단계에서 별도로 주입한다"고 명시
되어 있다). 필러어, ASR 용어 오인식, 조사 탈락, 숫자 표기 붕괴, 화자분리
뒤바뀜 시뮬레이션을 포함한다.

## 7. 알려진 한계 / 후속 과제

- 100문100답 PDF를 아직 확보하지 못해 소분류 커버리지 29종 중 16종이
  실코퍼스(FAQ 3사이트 수집분, 201건) 기준 커버리지 0건이다. 합성 생성
  격자 자체는 29종 전부를 돌았으므로 학습 데이터 공백은 아니지만, 프롬프트
  다양성의 실증적 근거(실제 문의 표현)가 약한 소분류가 존재한다는 뜻이다.
- 표본이 112건으로 적어 클래스당 positive가 7~23건 수준이다. 실데이터가
  들어오면 이 합성셋은 보강용으로 남기고 실데이터 비중을 올리는 방향이
  맞다.
